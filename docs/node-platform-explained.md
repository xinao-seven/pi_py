## 1. 主线：五块不是并列的，是围绕 M2 长出来的

大多数人介绍这几个模块时会说「我做了观测、任务、恢复、计划、子任务」——听起来是五个独立功能。
更准确的说法是一条主线：

> **M2（任务）是中心。M1 在旁边观察它，M3 保护它，M4 让模型用工具去写它，M5 派更多人来写它。**

展开一点：

| 里程碑 | 一句话 | 和 M2 的关系 |
| --- | --- | --- |
| **M1** 可观测 | 每次运行花了多少钱、慢在哪、工具可不可靠 | **在旁边看**：只读观测，可丢可关，绝不反过来影响任务 |
| **M2** 任务领域 | 把「一件事做到哪了」变成可持久化、可并发、可验证的实体 | **本体** |
| **M3** 断点续跑 | 崩溃/重启后，识别中断、解释现场、安全继续 | **保护它**：租约 + 在飞动作 + 恢复清单 |
| **M4** Plan | 让模型用结构化工具产出计划，而不是写一段作文被正则去抠 | **用工具写它**：Plan 是 Task 的受控视图 |
| **M4.1** 提问通道 | 工具挂起 → 弹窗 → 回答回流 | **让「等人」这件事只有一个真相源** |
| **M5** Subagent | 模型能派人去干会污染上下文的活 | **派更多执行者来写它**（继承父任务绑定） |

讲的时候**先给这条主线，再展开细节**，听的人就不会觉得是五个独立功能。

还有一条**贯穿的性质差异**，也值得单独说（§6.3）：同一个数据库里住着两种性格完全不同的数据——
M1 是「可丢的观测」，M2/M3 是「不能丢的状态」。

## 2. 名词扫盲：用装修比喻翻译一遍

| 项目里的词 | 大白话 | 装修比喻 |
| --- | --- | --- |
| **进程** | 一次运行的程序实例，有自己的内存和编号 | 一支施工队。**两支队伍不共享记忆，只能通过工地上的纸片交流** |
| **任务 Task** | 一件要做完的事 | 一张**施工单** |
| **步骤 Step（任务里）** | 施工单上的一行 | 拆墙、改水电、贴砖 |
| **run** | 一次「出门干活」：从收到指令到彻底安静下来 | 工人出工一次。**一条消息 ≈ 一个 run** |
| **步骤 Step（trace 里）** | 一次技术动作：一次模型请求、一次工具调用 | 出工期间干的**某一件事**（⚠️ 和上面那个「步骤」完全不是一个东西，见 §6.1） |
| **在飞 inFlight** | 此刻手上正拿着的那个活：**已经开工、还没收工** | 手上正拿着的那块砖 |
| **租约 lease** | 一张贴在门口的许可证，写着「张师傅，租到 10:05」 | 施工许可证 |
| **心跳 / 续期** | 每 10 分钟去门口换一张写着新到期时间的许可证 | 换许可证 |
| **owner** | 许可证上的署名，进程启动时生成一次，全进程共用 | 署名「张三-这次开工的编号」 |
| **副作用** | 干完之后世界变了，回不去了 | 砖贴上去就贴了 |
| **恢复清单** | 重启后列出「看起来没人干活、但活没干完」的任务 | 门口的告示 |
| **策略拦截** | 被正确拦下的调用（不是失败！） | 保安拦住了违规操作 |
| **前缀缓存** | 大模型对请求最前面一段的复用 | —— |

### 2.1 三个必须精确的说法

**① 租约有「两个单位」，不是一个。**

- **保护对象 = 任务**（一个任务一张许可证，不是整个工地一张，也不是每个工人一张）；
- **持有者身份 = 进程**（进程启动时生成一次，全进程所有任务共用同一个署名）。

所以判定是纯比较：**纸没过期 && 署名 ≠ 我** → 被占（409，任务只读）。
同一进程重复 acquire 自己的任务**不算被占**（否则续期会把自己锁死）。

**② 「崩溃的进程没法清理自己留下的痕迹」——这是整个恢复设计的根。**

崩溃的进程**没有机会执行任何代码**，所以磁盘上任何「我在干活」的标记都必须**能自己过期**。
不能用 `running = true`（崩了没人改成 false，任务永远卡死），只能写「**我租到 10:05**」。

> **租约的全部秘密：把「谁还活着？」这个无法回答的问题，换成「这张纸过期了没有？」这个可以回答的问题。**
> 心跳存在的唯一理由，就是让活着的人不断把到期时间往后推。

由此也能解释一个现象：**重启后旧租约不是立刻失效，而是最多 30 秒后失效**（因为没人续期，时间自然走完）。
这是「用时间代替探活」的固有滞后，是刻意接受的代价（见 §12 已知限制）。

**③ M3 管的是「进程没了」，不是「某个请求卡住了」。**

| 故障 | 进程还活着吗 | 谁负责 |
| --- | --- | --- |
| 进程崩溃 / 被强杀 / 重启 | ❌ 没了 | **M3**（心跳停了 → 租约过期 → 判中断） |
| 模型接口卡住 / 超时 / 报错 | ✅ 还在，心跳照常续 | SDK 的自动重试 + 用户点中止 |

这是一个很常见的误解。判据很简单：**只要进程还活着，心跳还在续，系统看到的就是「有人在正常干活」，不会判为中断。**

## 3. M1 可观测：定义口径，而不是「把日志存数据库」

### 3.1 机制（大白话）

```
SDK 事件流
  └─► 会话注册表发布事件（publish）
        └─► 顺手调一下账本：记一笔（唯一插桩点）
              └─► 写进队列（250ms / 200 条攒一批）
                    └─► 一个事务批量落 SQLite，同时增量更新预聚合表
```

### 3.2 三个精确的说法（面试最容易被追问的地方）

**① 不是「订阅」，是「插桩」。**

- **订阅者只有一个**：会话注册表（它订阅 SDK 事件、转发给 SSE）；
- **账本不是订阅者**——它是在注册表那个**已有的汇聚点上被顺手调一下**。

为什么这个区别要紧：如果是「加一个监听者」，就要回答「监听器抛错怎么办」；
而「在已经要执行的代码里加一行调用 + **内部全部 try/catch、异常只写警告**」，
回答的是同一条硬约束：**观测系统不能把被观测的系统搞挂**（宁可丢一条记录）。

**② 前端不读数据库，走 REST；而且读之前会先强制刷队列。**

保证「刚发生的事件立即可查」，同时不越过队列、不给浏览器数据库权限。

**③ 「分析」主要不在前端——聚合在写入时就做完了。**

- 三张预聚合表在 **run 结束 / 工具结束的那一刻**就增量累加（`INSERT … ON CONFLICT DO UPDATE`）；
- 为什么：实测过 **20 万行全表分组聚合 ≈ 96ms**，这是当时唯一真正的性能风险点；
- 分位数（p50/p95）确实要扫明细，所以用「**范围内最近 2000 条有界样本**」折中（样本不足即精确值）。

### 3.3 两个最值钱的口径（务必记住）

**① run 的边界取 `agent_settled`，不取「开始/结束」。**

SDK 在自动重试、上下文压缩、队列续跑时会**多次发出「开始了」**。按「开始」切分，
一次用户请求会被拆成好几个 run，**成本统计直接失真**。只有 `agent_settled` 在所有自动行为收敛后才发一次。

**② 策略拦截 ≠ 工具失败。**

SDK 对「被审批拒绝」和「工具真的报错」**都只发同一件事**（工具执行结束且失败）。
如果不区分，「工具失败率」从第一天就是错的——它把「**成功拦下了一条删除命令**」统计成了「工具不可靠」。

所以账本额外收集归因（审批结算上报 / 规划期拦截上报 / 结果文案兜底），
失败率只统计 `未被拦截 && 确实失败` 的调用，被拦下的单独计 `blocked`。

### 3.4 三种性格（写进文档就是「诚实」）

- **默认不落正文**：只存 `sha256` 摘要 + 字节数 + 120 字符预览；正文要显式开开关，且落库前已脱敏（三层：密钥键名 → 密钥形态 → 大字符串只扫前缀）；
- **攒批**：不是每条立刻写，250ms / 200 条一个事务；
- **可丢可降级**：队列超限丢最旧并计数、连续失败进降级、**`PI_NODE_TRACE=0` 整体关掉后行为与没有它时完全一样**；降级状态在面板上可见（不让用户把「没数据」误读成「没花钱」）。

### 3.5 面试要点

- 「加这套东西会不会拖慢 agent？」→ 实测 `record()` 同步开销 **p50 0.004ms / p95 0.011ms**，出现 5.5ms 的那次是**每 200 条一次的批量 flush**，不是单条开销；这个数字由测试守门。
- 「为什么不用 OpenTelemetry？」→ 这是**单机自托管工具**，不是分布式服务。要的是 SQL 可查 + 面板直出，不是 span 瀑布图；零依赖、可离线、**可整体关闭**比重协议更重要。字段设计本身就是 span 的等价物，导出层可加。

## 4. M2 任务领域：两条命根子

### 4.1 结构

**两张表**：`tasks` + `task_steps`。

步骤**独立成表**不是随便拆的：步骤要按顺序排、要单独改、会被计划反复整批替换——塞进一个 JSON 字段里做 diff 会很痛苦。

关键字段：`origin`（人工 / 计划）、`revision`（版本号）、`verification`（完成声明）、
`evidence`（完成证据）、`execution`（运行时状态：租约 / 心跳 / 在飞 / 最近副作用）。

### 4.2 命根子 1：状态是**派生**的

```
空步骤 或 全没开始              → 没开始
全部完成 / 跳过                 → 完成
任一卡住                        → 卡住（需要人介入，比「进行中」更该被看见）
只要有一步离开「没开始」         → 进行中
```

三个刻意的取舍：

1. **「已开工」不能只看有没有「进行中」的步骤**：模型通常是「做完一步、在还没开始下一步时就更新状态」，
   只认「进行中」会把「2 步做完 1 步」显示成**尚未开始**，与事实正相反。
2. **只有「用户取消」是冻结的**：它是显式意图，不能被某次步骤变更拉回来；而「完成」是聚合结果——
   **删掉最后一个未完成步骤，任务就该回落**。
3. **手工设置的状态会在下一次步骤变更时被重新聚合**：这是故意的，**不允许存在「任务说完成、步骤还挂着」的隐藏状态**。

> 一句话：**能算出来的东西不要存。** 少一份状态，就少一处可能自相矛盾的地方。

### 4.3 命根子 2：乐观并发

每个写请求都必须带版本号，用**一条 SQL 原子判断**：

```
UPDATE … SET revision = revision + 1 WHERE id = ? AND revision = ?
```

按影响行数判定成败；失败返回 409 并带上**当前真实版本**，前端可据此刷新重试。

为什么不用锁：单进程、单连接、同步执行，冲突窗口本来就极小，冲突的代价只是「重试一次」。
用一条 SQL 把「读到的版本」和「写入」绑成原子操作，比引入锁管理器简单且不会忘记解锁。

**M3 逼出来的语义修正（跨模块的因果关系，很能加分）：**

- **版本号 = 用户可见内容的版本**。心跳、租约、在飞这些**运行时写入不占版本号**（仍落库、仍广播）。
  否则模型思考期间心跳一直顶版本号，它手里的版本持续过期，计划更新和面板编辑频繁 409。
- **「改完之后还是原对象」＝ 无变化**：不写库、不广播、不动版本号。否则幂等命令（如「继续执行」）
  会白白作废模型和面板手里的版本。
- **执行态写入也必须走任务服务**（乐观锁 + 广播），不能绕开直接写库，否则面板手里的版本会**静默落后**，
  用户「什么都没改却被拒绝」。前端为此加了「409 自动刷新后重试一次」。

### 4.4 其余值得说的

- **SSE 广播规则**：绑定会话的任务只推给该会话；未绑定的推给 `cwd` 匹配的活跃会话；未打开的会话靠 REST 拉最新（**广播是加速，不是真相源**）。
- **任务变更不进前端流式状态机**：因为「任务变了」不等于「Agent 正在跑」，混进去界面会误判。
- **半成品接口不占位**：`/resume`、`/recovery` 在 M2 阶段**故意不存在**（而不是返回假数据）——接口存在会让调用方以为功能已经有了。

### 4.5 面试要点

「任务和 trace 怎么区分一致性要求？」→ 见 §6.3。这是 M2 最值得讲的一条设计判断。

## 5. M3 断点续跑：难点不是「记住进度」

### 5.1 先破误解

大多数人以为断点续跑 = 「把执行到第几步存下来」。**存进度是最容易的部分**（M2 天然做到了）。

真正的难点是一句话：

> **崩溃的那一刻，那个正在执行的动作，到底落地了没有？**

而猜错的代价是**不对称**的：

| 猜错方向 | 后果 |
| --- | --- |
| 把「已落地」当成「没落地」 | **重复副作用**（覆盖用户代码、重复提交），**不可逆** |
| 把「没落地」当成「已落地」 | 步骤被错误跳过，任务报完成但活没干 |

两种都错，但**前者破坏性远大于后者**。所以整套设计的基调是：**宁可停下要人确认，也绝不自动重放**。

### 5.2 三条不可让步的规则（背下来）

1. **只列不跑**——恢复清单不自动执行；
2. **无法判定副作用必须人工确认**；
3. **产物在就补记完成，绝不重跑**。

### 5.3 机制 1：租约（谁在跑）

- `owner = 进程号 + 本次开机标识`，服务启动时生成**一次**，全进程共用；
- TTL 30 秒，每 10 秒续期（TTL 的 1/3，**容忍单次续期失败或事件循环卡顿**）；
- 存在**任务自己**的 `execution.lease` 里——不需要额外的锁表，也不需要清理孤儿锁；
- 过期可抢占；被别的活跃进程持有时 → 409 `task_leased`，任务只读。

**为什么 owner 要带「本次开机标识」**：让「重启」这个事实**天然保证旧租约不会被续期**
（新进程署名必然不同），于是**根本不需要记录「上次是谁在跑、它现在还活着吗」**。
一个随机数换掉一整套清理逻辑。

**中断判定只两条**：任务还在进行 **且** 租约不活跃。

刻意**不区分**崩溃、强杀、优雅退出——因为**重启后这三者在库里长得一模一样**（活没干完，但没人在干）。
已经「卡住」的任务不进清单（它已经在面板上等人处理了）。

### 5.4 机制 2：在飞动作 + 三级副作用

事件钩子记录「此刻手上拿着什么」：模型思考 → `turn`（无副作用）；工具开始 → `tool`（带副作用等级）；工具结束 → 清空。

| 工具 | 等级 | 理由 |
| --- | --- | --- |
| `read/grep/find/ls/…` | `none` | 结构上不可能改工作区 |
| `edit/write/apply_patch/…` | `write` | 写类工具 |
| `bash` **命中审批规则** | `write` | **复用同一套审批规则** |
| `bash` **未命中规则** | **`unknown`** | 普通命令也可能是写（`python -c "open(...)"`）——既不能证明只读，也不该假设无害 |
| MCP / 未知工具 | `unknown` | 同上 |

**「复用审批规则」的意义**：审批、规划期权限、恢复副作用等级**三者永远一致**，
不会出现「审批说危险、恢复说没事」。

**比规范更保守的一处（最有含金量的细节）**：工具执行**结束时，步骤还没有被打勾**。
所以「文件写完了、还没打勾就被杀」这个窗口里，如果只看在飞（那时已清空），会被判成
「**崩在两步之间 → 可以自动继续**」——**这正是重复副作用最典型的来源**。

修法：额外记一笔「最近有副作用的动作」，并且只在它**属于当前步骤的本次尝试**时才算数。

> 妙处在后半段：用户点「重试这一步」之后，这一步的开始时间被更新，那笔旧标记**自然失效**——
> **不需要任何额外的清理代码**。用**不变式**表达生命周期，而不是写清理逻辑。

### 5.5 机制 3：三种恢复动作

| 情况 | 处理 |
| --- | --- |
| 无副作用（含「崩在两步之间」） | **自动继续** |
| 有副作用 + 这步声明过成品文件 | 先**只读看文件在不在**：在 → **补记完成（绝不重跑）**；不在 → 停下 |
| 有副作用但无法验证 / `unknown` | **必须人工确认** |

三个细节：

- **只有文件类产物能自动验证**：命令类验证**故意不在 M3 执行**——那等于绕过审批链路跑任意 shell，
  与「危险命令必须人工确认」直接冲突。M3 只做只读 `stat`（不创建、不修改）。
- **「产物在」是补记不是跳过**：补记时写上证据（「恢复时验证产物已存在：xxx」），
  所以**你能看出这一步是模型做的还是恢复流程确认的**。
- **`retry_step` 是唯一逃生门**：产物不在时默认路径是「释放租约 + 标成卡住 + 返回 409」，
  只有用户显式选择「重试当前步骤」才继续，且摘要里会注明「产物未找到，先核对工作区」。

### 5.6 续跑的六步：每一步失败都有确定归宿

```
1. 校验          → 不满足就 409，绝不静默开跑
2. 取租约        → 取不到就 409 task_leased，不做任何后续动作
3. 副作用验证     → 通过则补记完成；失败则标卡住 + 409（或按 retry_step 继续）
4. 打开会话      → 失败则释放租约 + 标卡住 + 409（不崩）
5. 注入恢复上下文  → 隐藏消息 + 绑定会话与任务
6. 发 prompt + 保活 → prompt 失败则回滚（停续期、释放租约）
```

**这个结构本身就是设计**：每一步失败都有确定归宿，而且失败时会**回滚自己造成的状态改动**——
不会留下「租约被占但没人在跑」的僵尸状态。

### 5.7 恢复上下文：隐藏注入 + 强制对账

摘要以「**界面不显示、模型可见、只注入一次**」的方式注入，内容包括：
任务标题与目标、**第几次尝试**、已完成步骤**及其证据**、当前步骤、后续步骤、中断说明、副作用处理说明。

然后要求模型：

> **先复述当前状态与已完成的工作，确认没有冲突，再继续。**

这是一个**强制对账**动作——防止它拿着崩溃前的假设继续干。成本是一轮对话，
收益是避免基于错误假设执行。这是**对模型的行为约束，不是能力约束**。

### 5.8 与其它模块的接缝（M3 真正的价值）

| 对接 | 内容 |
| --- | --- |
| **M2** | 逼出版本号语义修正（运行时写入不占版本号）+ 执行态写入必须走任务服务 + 前端 409 自动重试 |
| **M4** | 计划执行**复用同一套租约与绑定**；暂停/放弃 = 主动释放租约；`replan` 在 M3 返回 `replan_unavailable`，M4 接手后只对计划任务开放；产物验证纯函数被 M4 复用 |
| **M5** | **没有为子会话写一行恢复代码**：子会话继承父任务绑定，于是它的在飞动作/副作用写进父任务、成本归因到父任务、取消级联；`TaskRunner.stop` 会级联中止子任务 |
| **M1** | 语义上刻意分开：trace 是可丢的观测、任务是强一致的状态（见 §6.3） |

### 5.9 面试要点

- **「为什么不直接用数据库事务和行锁？」** → 锁的生命周期绑在连接上，进程一崩锁就悬空，需要额外检测与清理。
  租约是「带过期时间的占用标记」：**把存活判定从「连接是否活着」换成「时间戳是否过期」**。
- **「两个进程同时 resume 会怎样？」** → 先取租约（在一切动作之前），第二个得 409，任务只读。
- **「凭什么说不会重复副作用？」** → 三道：写副作用在步骤完成前一直留标记（不是工具一结束就清）、
  产物在就补记而不重跑、`unknown` 一律要确认。**自动路径里没有任何一条会重放写操作**。

## 6. 跨模块的三条主线（讲的时候一定要给）

### 6.1 ⚠️ 「步骤」这个词在两个地方意思完全不同

| | trace 里的 step | 任务里的 step |
| --- | --- | --- |
| 是什么 | 一次**技术动作**（模型请求、工具调用、审批等待） | **施工单上的一行**（业务步骤） |
| 谁在用 | M1，用于统计「哪个工具慢、哪个老出错」 | M2，用于表达「这件事做到哪了」 |
| 人看得到吗 | 点开「用量」面板才看到 | 天天在面板上看着 |

**同一个词，两个东西。** 想清楚这个，「账单」和「施工单」就不会再混。

### 6.2 `run` 和 `task` 也不是一回事

| | run | task |
| --- | --- | --- |
| 是什么 | 一次出门干活（从开始到彻底安静） | 一张施工单（一件要做完的事） |
| 粒度 | 一条消息 | 可能跨多条消息、多次重启 |
| 归属 | M1 的概念 | M2 的概念 |
| 关系 | **一个 task 里有很多个 run** | 一个 run 可以没有 task（普通问答） |

### 6.3 两种性格：可丢的观测 vs 不能丢的状态

| | M1 trace | M2/M3 任务 |
| --- | --- | --- |
| 定位 | 事后复盘的观测 | 决定下一步干什么的状态 |
| 写入 | 走队列、攒批 | **同步落库** |
| 失败 | 降级、丢弃、写警告 | **必须冒泡成 API 错误** |
| 能不能关 | 能（关了行为不变） | 不能 |
| 存的粒度 | 明细可清理、只保留聚合 | 必须完整 |

> **不是所有数据都值得强一致，但用户能看见的动作必须强一致。**
> 它们住在同一个数据库文件里，但走完全不同的两条写入路径——这不是重复设计，是刻意的区别对待。

## 7. M4 Plan 模式：把状态从「模型的措辞」里拿出来

### 7.1 旧设计为什么崩（8 个缺陷，一个根因）

旧实现把**状态机的迁移条件交给了模型的文风**：

- 模型必须在回答里写出特定格式的标题和列表 → 服务端**用正则从自由文本里抠**计划；
- 模型必须写 `[DONE:n]` 标记 → 服务端**靠标记**认为第 n 步完成。

**根因**：正则抠不出来，计划就永远不存在，「确认并执行」必然失败，面板永远停在「正在生成计划」。
模型只要换一种表达方式，整个功能就**静默失效**。

更本质的是第二点：**系统层面对「完成」没有任何验证能力**——模型说做完了就做完了，漏写一次标记，执行态永不收敛。

> 方向一句话：**把「状态」从「模型的措辞」搬到「数据库 + 工具契约」上。**

### 7.2 三条不变量

1. **只有用户能推进关键状态**：从「待确认」到「执行中」必须由用户动作触发，模型在规划期**没有写工具**，无法绕过确认改工作区；
2. **步骤完成必须有证据**：要带 summary / 命令+退出码 / 改动文件；声明了验证方式时服务端会校验，不符则返回**可读的工具错误**让模型补齐；
3. **状态只有一份**：任务表是唯一真相源，前端看到的计划视图是**现算的投影**，任何一方写入后其它方通过 SSE 看到同一份。

### 7.3 结构性决策：Plan 是 Task 的受控视图

一次规划 = 创建一个 `origin='plan'` 的任务。**没有自己的表、没有自己的状态，连 id 都跟任务同一个。**

好处是连锁的：计划自动获得任务的持久化、乐观并发、面板、SSE 广播，**以及 M3 的租约与断点续跑**；
成本账本里的 run 也通过任务 id 关联上——「这个计划花了多少钱」是免费得到的。

**状态只存四种意图**（草稿中 / 待确认 / 执行中 / 已暂停）；
「已完成 / 已放弃」**不落库**，由任务状态推导。少存一份状态就少一处可能自相矛盾的地方。

（细节：任务被步骤聚合为「卡住」时，计划投影成「已暂停」——因为「有步骤阻塞在等人」和「用户暂停」
在界面上需要的是**同一个动作**，分成两种状态只会让前端多一个分支。）

**计划一进入规划就落库**，而不是等提交才建：因为「正在调研」这段状态同样需要被持久化和被看到。

### 7.4 工具契约：模型不写任何标记

五个计划工具 + 一个通用提问工具：

| 工具 | 作用 |
| --- | --- |
| `propose_plan` | **模型提议**进入规划（走提问通道问用户，用户点头才真的开启） |
| `submit_plan` | 提交计划（结构化参数：标题 + 步骤数组 + 每步验证声明） |
| `update_plan` | 带版本号修订 |
| `complete_step` | 带证据标记完成（服务端校验） |
| `block_step` | 阻塞 + 原因 |
| `ask_user` | 通用提问通道（**不属于计划**，见 §8） |

三个要点：

1. **参数是结构化的**——「正则解析」这一整类问题被结构性消灭；
2. **返回错误而不是假成功**：参数不自洽、版本陈旧、验证不通过，都返回**可读的工具错误**，
   模型据此自我修正——这是「模型能收敛」的前提；
3. **没计划时误调 `submit_plan` 不会造出计划**，而是报错——挡住「模型自己开计划把自己锁进只读态」这条风险。

### 7.5 证据校验分级：不假装强校验（最值得讲的「诚实」）

| 声明 | 校验方式 | 强度 |
| --- | --- | --- |
| `file` | 查产物是否真的存在 | **最强**（查的是外部世界的事实） |
| `command` | 只验证「证据里确实有这条命令，且退出码符合预期」 | 弱 |
| `manual` | 要求非空结论 | 需要人读 |

**为什么服务端不自己重跑 `command`？** 因为那等于**绕开工具审批链路执行任意 shell**——
我们花大力气建立的「危险命令必须人工确认」，不能为了「更强的校验」在这里开后门。

所以口径明确写成：`command` 验证的是「**确实跑过并如实上报**」，不是「跑对了」。
模型谎报在技术上仍可能，**但那是可审计的谎言**（证据留在账本里）；
而服务端偷偷执行任意命令是不可控的风险。两者不对称，选前者。

### 7.6 规划期权限：能力分类，不是白名单

旧实现用一条**正则白名单**放行只读命令，结果把最常用的验证命令全拦了
（`tsc --noEmit`、`pnpm test`、`npm run build`）——**规划期跑不了验证，计划质量自然差**。

现在的判定是三层，顺序即优先级：

1. **先跑审批规则**（危险/敏感命令一律不放行）——**同一套判定同时服务审批、Plan 权限、恢复副作用**；
2. **把命令按 `;` `&&` `||` `|` 拆段，每段都要放行**——防 `npm test && rm -rf src` 这种「一段合法一段破坏」（拆段要处理引号）；
3. **每段按程序名归类：只读 / 验证 / 写 / 未知**，**未归类 = 未知 = 不放行**。

> **白名单是「默认拒绝正确的」，能力分类是「默认拒绝未知的」。**

判定里的深度细节（讲这些显得真的做过）：`git` 按子命令判（`status/log/diff` 只读，`commit/push` 写）；
包管理器同理（`npm run` 算验证、`npm install` 算写）；`npx <tool>` 只放行已知工具——
**不放行「npx 任意包」**（等于执行未知代码）；`sed/perl` 看有没有 `-i`；
`node -e`/`python -c` 扫描脚本片段里的写文件、子进程调用等模式。

**拦截时返回人类和模型都能读的原因**，而不是一句 `denied`——模型据此改用只读方式，而不是反复重试同一条命令。

### 7.7 缓存稳定性：一个反直觉的取舍（M4 最亮的点）

早期用「**改工具集**」兑现权限：规划期关掉写工具，计划结束再收回来。看起来是最小权限，做得很「正确」。但它有昂贵后果：

- 请求体顺序是 `[工具列表, 系统提示词, 消息…]`，而**前缀缓存从最前面开始比对**——
  改一次工具列表 → 系统提示词里的工具清单一起变 → **后面所有缓存断点全部失效**；
- 更贵的第二个漏点：规划上下文**每轮删旧加新**，而注入的消息会被转成用户消息**夹在历史中间**，
  于是等于**从注入点往后每轮改写历史**——计划越久越贵。

修法两条：

1. **工具集在整个会话生命周期内恒定**：计划开始/结束**完全不改工具**，只读改由**调用拦截**兑现；
   - **代价明确接受**：模型在规划期可能试一次写工具被拦（多一轮 + 一条可读的拦截理由）。
2. **注入去抖**：注入前先比对历史里最后一条同类注入的正文，内容相同就不注入。
   于是「状态没变 → 历史一字不动 → 缓存命中」；只有状态跃迁时才改写一次。
   **失配从 O(轮数) 降到 O(状态数)。**

并且**这个优化是可量化的**：面板加了「缓存命中率」KPI，同一会话同等轮数下前后对比即可。

> 两句话记住：
> **一次被拦的调用，远比整段前缀失配便宜。**
> **当「最小权限」和「成本」冲突时，可以把权限从「能力裁剪」改成「调用拦截」——因为拦截是 O(1) 的，而重建前缀是 O(上下文) 的。**

### 7.8 `propose_plan`：提议权给模型，决定权留给用户

模型可以问一句「要不要先进入规划模式」，用户选「先规划」才真的开启，**并且本轮工具结果里直接带上规划期的用法说明**，模型当轮就知道下一步该干什么。

三条边界：用户选「直接做」/ 超时 → **不建计划、不进只读态**；已有计划 → 报错让模型改用提交/更新；
提问通道不可用 → 返回 `unavailable`（而不是把工具弄成失败）。

**为什么不做「模型一提计划就自动开启」**：简单任务也会弹确认面板（**过度规划**），
且模型一提交计划就把自己**锁进只读态**直到用户确认（**自锁**）。两条风险都不接受。

### 7.9 执行期的修改边界

允许执行期调整，靠「**按标题复用进度**」：标题（归一化后）相同的步骤**沿用原来的 id、状态与证据**，其余按新步骤创建。

由此得到准确边界：**不能删除或重命名已经开始/已完成的步骤，但没开始的部分可以随便调整**。

（弯路值得讲：初版是「执行期一律禁止替换步骤」——听起来安全，但把要修的场景也挡掉了。这条是被**评测用例**抓出来的，不是单测。）

### 7.10 CLI 兼容

会话 JSONL 只在计划创建/采纳时写一条**指针**（不再随状态变化追加完整快照）。
旧快照**保留不删**（审计痕迹，CLI 侧本来也不解析）。
呼应最高约束：**会话 JSONL 是原版 CLI 的资产，只允许追加，不允许改写和删除。**

### 7.11 验证体系（这段很能证明「工程能力」）

| 层 | 作用 |
| --- | --- |
| 单测 | 边界、纯函数、状态机分支 |
| **spike**（真实 SDK + 离线假模型，进 CI 门禁） | 跑完整旅程，并断言「**模型全程零标记**」；工具集在四个时点一字不变 |
| **eval**（golden set + 门禁指标） | pass@1、计划一次通过率、零残留旧标记等 |

**为什么必须有 spike/eval**：M4 抓到的 5 个真实缺陷，要么出在**SDK 交互边界**，要么出在**真实时序**里——
**单测全绿也发现不了**。它们不该被当成可选脚本，而应该是门禁。

（一个诚实点：eval 里「工具调用失败率 16.7%」不是越低越好——它**包含刻意制造的拒绝**
（错退出码、缺产物、陈旧版本）。这个指标的价值在**多次运行之间可比**。）

## 8. M4.1 提问通道：让「谁在等用户」只有一个真相源

### 8.1 机制与四条取舍

工具挂起 → SSE 推「有提问」→ 前端弹窗 → 用户回答 → **答案作为工具返回值回流**，模型在同一次工具调用里继续。

1. **挂起，而不是结束本轮**：旧做法（结束本轮 + 用户自由文本回复）会让模型猜「这条消息是回答还是新需求」；
2. **必须有确定的失败路径**：超时 / 取消 / 中止 / 会话关闭都按「未回答」结算，并要求模型**按最合理假设继续并写明假设**——不是报错，也不是永久挂起；
3. **一次只允许一个挂起提问**：前端只有一个弹窗；需要并行问多件事，就把它们放进同一次调用（一次最多 8 题）；
4. **默认允许自由输入**：选项永远可能不全，逼用户在预设项里选是最讨厌的交互。

### 8.2 为什么它不是 Plan 的一部分

提问是**通用交互**，任何会话都激活，计划结束后依然可用。

并且 `PlanView` 里的「提问」字段被**移除**了——**「谁在等用户」只有一个真相源**（挂起队列 + 会话状态快照），
避免两处状态互相矛盾。这条原则在 M5 又用了一次（子会话不能提问）。

### 8.3 一个很典型的「只有真实浏览器能发现」的缺陷

前端在拷贝流式状态时**逐字段复制**，漏掉了「挂起提问」这个字段 →
服务端推的提问状态被**静默丢弃** → 模型挂起等待，但界面不弹窗。
（后端与评测都正常。）

教训：**新增状态字段时，「拷贝/映射」这类地方是静默失败的温床**；并且修完还要**重新构建前端产物**，否则线上加载的仍是旧 bundle。

## 9. M5 Subagent：让子任务成为「已有设施的第 N 个用户」

### 9.1 为什么不能直接用官方扩展

官方 `subagent` 文件扩展的本质是「**另一个进程里的另一个 pi**」（`spawn` 独立进程）。四个实测事实让它不可用：

| 事实 | 后果 |
| --- | --- |
| 预设写死了本机未鉴权的模型 | 子进程**启动即退出**，而且**失败原因对用户不可见** |
| spawn 独立进程 | 拿不到 Web 的审批通道、不进 trace 树、不受租约约束、离线没法评测 |
| 只回事件流、用量靠父进程累加 | 账本看不到这次委派的成本 |
| 它被自动加载进**每个** Web 会话 | 工具列表里常驻一个**必然报错**的工具，**模型会反复去踩** |

最后一条特别值得强调：**失败的形态不是「报错」，而是「模型一次次尝试一个注定失败的工具」**——
这是最消耗 token 也最消耗用户信任的失败方式。

**决策：内联实现 + 同名接管。** 自己实现 `subagent` 工具，并把 `subagent` 加进「被内联实现接管的扩展目录」名单。

> 机制：**只影响本服务的资源加载，不动用户磁盘上的任何文件，CLI 照常加载它自己那份。**
> 所以模型在 CLI 和 Web 里学到的仍然是同一个工具名，行为却各自成立。

### 9.2 核心判断：子会话就是一个会话

官方是「起一个新进程」；我们是「**在会话注册表里再注册一个会话**」——走**完全一样的创建路径**。

这一个决定带来一连串「免费」的能力：**审批**（同一个中枢，无法绕过）、
**SSE**（天然接进既有通道）、**trace**（账本只认会话 + 事件，不需要新埋点）、
**任务/租约**（M2/M3 的绑定同样生效，取消可级联）。

> 面试金句：**我没有为子任务造一套新的执行设施，而是让它成为已有设施的第 N 个用户。**
> 反过来，如果当时选了「起子进程」，上面四项每一项都要单独实现一遍，而且各自要面对一致性。

### 9.3 三条不变量

1. **不能递归是结构保证**：到深度上限的子会话，**在那条创建路径上根本不注册这个工具**——
   模型连「试一下」的机会都没有，而不是运行时拦截。
   > **结构上不存在的可能性，不需要用规则去防。**
2. **只读预设真的只读**：子会话的工具集**就是预设声明的工具集**，**不并入** MCP 工具 / 计划工具 / 提问工具。
   （差点出事：M4 为「预设白名单会把内联工具挡在门外」引入了「并入内联工具」的逻辑，
   如果对子会话也这么做，「只读预设」立刻不成立——所以这里是**反向利用同一个机制**：对父会话并入，对子会话必须关掉。）
3. **一定要收尾**：成功 / 失败 / 超预算 / 超时 / 取消 / 服务关闭，六条路径全部释放子会话。
   因为子会话是**会改工作区**的活的东西，漏掉任何一条就会留下「还在改文件但没人看得见」的会话。

### 9.4 预算：建立在「对方真的会上报」的指标上

初始设计最自然的单位是美元。**但本机用的 deepseek 上报的成本恒为 0**——
也就是说「美元上限」**形同虚设**，子任务可以无限跑而预算永不触发。

于是改成以**轮数 + token + 时限**为主，美元只在 provider 确实上报时才生效。默认值按预设分档。

而且**超预算不是失败**：中止，但**把已经产出的摘要带回来**——花掉的钱不能白花。

> 金句：**预算必须建立在对方真的会上报的指标上，而不是你以为它会有的指标上。**

### 9.5 失败是数据，不是异常

- **只有「连子会话都没能起来」才抛错**（SDK 标为工具错误）；
- **跑起来了但失败 / 超预算 / 超时 / 被取消 → 是「结果」**，正常返回，带上状态、原因、用量、轨迹。

为什么这个边界重要：异常会让父会话倾向于重试同一条路；**结果**才能让它做判断
（缩小范围重试 / 换预设 / 自己干）。工具文本里甚至直接给出这个建议。

### 9.6 只回摘要，且明确要求父会话自己核实

父会话拿到的是**摘要 + 轨迹计数（`bash×2, read×5`）+ 用量**，**不是子会话全文**。

并且工具说明里明确写：**「把它当作线索而不是结论——涉及改动的结论要自己核实」**。
真机验证里确实观察到父会话拿到「45 个 .ts 文件」后**自己又跑了一次命令复核**。

> 设计意图：**委派省的是上下文成本，不是验证责任。**

### 9.7 审批：必须挂到「人真正能看见的那个会话」上

这里踩过真实的坑：早期把审批事件发到**发起审批的会话**（子会话）的事件流上——
**而子会话没有界面、没人订阅那条流** → 用户看不到弹窗 → 30 秒超时按拒绝 → 表现为「**委派莫名其妙失败**」。

正确机制两条：

- 挂起项带上**父会话 id + 预设名**，事件发到**父会话的流**上（弹窗写「子任务 scout 请求执行 …」）；
- `approve_tool` 命令**仍然只发父会话 id**，中枢按「这个挂起项属于该父会话」回退匹配。

> 通用原则：**任何需要人介入的机制，都必须挂到人真正能看见的那个界面上。**

### 9.8 trace 树 + 任务继承（两条接缝）

- **trace**：子会话的 run 通过「父 run id」挂到**父会话当前那条 run** 下，meta 里记预设与深度。
  （顺手暴露了 M1 的一个 bug：收尾写入把 run 的 meta 抹成 NULL → 执行树断链。修法是「新值为空则保留原值」+ 账本收尾改为**合并**而不是覆盖。）
- **任务**：子会话**继承父会话当前的任务绑定**。于是：
  - 子会话的 token **算在父任务头上**（成本归因清楚）；
  - 子会话的在飞动作/副作用标记**写进父任务** → 崩溃后恢复清单看到的是「父任务当时正在跑一个子任务，副作用未知」；
  - **取消是级联的**（父中止 / 计划暂停放弃 / 会话删除 / 服务关闭 / 任务执行器停止，五个入口收敛到同一处）。

> **M5 没有为子会话写一行恢复代码，它自动被纳入了 M3 的保护范围。**
> 这是「子会话就是一个会话」那个决定的最大复利。

### 9.9 与 Plan 的边界：三处刻意的「不给」

| 不给 | 原因 |
| --- | --- |
| **Plan 模式** | 子任务再起一个计划状态机，会让「谁在等我确认」变得模糊——**一个会话同一时刻只应该有一个「在等用户」的状态** |
| **`ask_user`** | 弹窗归属会乱、父会话会被卡住；改为要求它「把缺什么写进摘要」 |
| **MCP / 计划工具** | 不并入白名单，否则只读预设不再只读 |

还有一个很诚实的现实：用户现有的 `scout` 预设带 `bash`，所以它**在规划期会被拦**（执行期正常）。
文档没有偷偷放宽策略，而是明写：**想让它在规划期可用，就把预设自己的 `bash` 去掉**——
**收紧预设，而不是放宽策略。**

（规划期的委派门禁是「**结构上只读**」：工具集必须完全落在 read/grep/find/ls 里，不能含 bash。
因为子会话是独立会话、不受规划期策略约束，所以**不能信任预设的自觉**。）

### 9.10 并发闸门：排队，不是拒绝

全局 3 个、每个父会话 4 个并发子任务，**超限排队**。

理由：模型在同一轮里发多个委派是**正常且被鼓励**的行为。如果超限直接报错，模型看到的是「工具失败」，
它会重试——既浪费轮次，又可能误判「委派不可用」。

顺带一个参数取舍：**工具不做「串行 / 并行」参数**，一次调用只管一个子任务，并行靠同一轮发多个调用。
理由很实在：**少一个参数维度，就少一类「参数写错却看起来在跑」的失败。**

> 顺带区分：**租约 vs 并发闸门**
> 租约（M3）防的是「同一个任务被两个进程同时跑」→ 超了**拒绝**（并行会重复副作用）；
> 闸门（M5）防的是「一次开太多子任务」→ 超了**排队**（排队是安全的，只是慢）。

### 9.11 评测：测试替身不能偏离真实装配路径

M5 把评测的装配从「手写的假工厂」换成了**真实的会话工厂**（只替换模型运行时）。

原因：原来的假工厂自己拼 SDK 调用，而**子会话根本不走那条路径**——
不换掉的话，**「M5 的评测只是在验证评测自己的实现」**。

> 面试金句：**测试替身一旦偏离真实装配路径，你测的就是替身，不是系统。**

## 10. 真实缺陷清单（讲这些最有说服力）

| # | 缺陷 | 发现方式 | 为什么单测抓不到 |
| --- | --- | --- | --- |
| 1 | SDK 的「工具列表」是**可用工具白名单**：不在名单里的工具调用时报「not found」，导致带预设的会话里计划工具完全不可用（MCP 同理） | spike | 只有 SDK 交互边界才暴露 |
| 2 | 心跳顶掉版本号 → 模型思考期间手里的版本过期 → 频繁 409 | eval | 真实时序 |
| 3 | 幂等命令也顶版本号（继续执行时白写一次） | eval | 同上 |
| 4 | 执行期一刀切禁止替换步骤，把要修的场景也挡掉了 | eval | 需求边界 |
| 5 | **子会话审批发到了没人订阅的流上** → 30 秒超时按拒绝 → 委派莫名失败 | 真机 | 只有真实浏览器/订阅者拓扑能发现 |
| 6 | 收尾写入把 run 的 meta 抹成 NULL → 执行树断链 | 真机 | 只在子会话场景可见 |
| 7 | 前端逐字段拷贝状态时漏了新字段 → 提问弹窗不弹（模型在等，界面没反应） | 用户实测 | 后端与评测都正常，**只有真实浏览器能发现** |
| 8 | 迁移直接改写已发布的 DDL → 已建好的库缺表，聚合查询直接报错（改成追加新版本迁移修复） | 开发中 | 只有「已有数据库」这个状态才能触发 |
| 9 | 连接泄漏：trace 关闭时没人关数据库连接（任务共用该连接） | 测试清理临时目录失败 | 只有在关闭路径上才暴露 |
| 10 | 漏提交文件导致 HEAD 不能编译（本地工作区能过、HEAD 过不了） | CI/换目录构建 | 教训：**提交前跑完整门禁，不能只看工作区** |

**结论性反省**：这些缺陷要么出在**外部系统交互边界**，要么出在**真实时序**，要么出在**只有真实浏览器/已有数据才能触发的状态**上——
**单测全绿也发现不了**。这就是坚持「spike + eval + 真机验证」三层门禁的原因。

## 11. 三条跨模块的不可让步规则

面试官问「你怎么保证不出事」时，直接答这三条：

1. **只有用户能确认执行**
   —— M3「只列不跑」（恢复清单不自动执行）+ M4「待确认 → 执行中必须用户触发」（模型在规划期没有写工具）；
2. **步骤完成必须有证据，并按声明的验证方式校验**
   —— 校验不过返回可读的工具错误，让模型补齐；
3. **产物在就补记完成，绝不重跑**
   —— 能验证就验证、能自动就自动、不能判定就停下问人；**自动路径里没有任何一条会重放写操作**。

## 12. 已知限制（主动坦白，反而加分）

| 项 | 说明 |
| --- | --- |
| 聚合时间分辨率 | M1 预聚合是「天 + 工作区」，自定义小时级窗口会按整天计入 |
| 崩溃后最多 30 秒才判「过期」 | 租约靠时间自然走完，不是立刻作废（「用时间代替探活」的固有滞后） |
| 进程被强杀 | trace 里会留下 `status=running` 的悬挂 run（正常关闭会收尾） |
| `command` 类验证不重跑 | 只验证「跑过且如实上报」；要变成强校验需要接进工具调用与审批链路 |
| 续跑一次只推进一步 | 多步连跑依赖模型在会话里继续 |
| 计划不支持并行步骤 | 步骤是有序列表；并行属于子任务范畴 |
| 面板无拖拽排序 | 接口已就绪（改 `position`），UI 未做 |
| 子会话的界面支持较浅 | 只有工具卡片里的摘要 + 轨迹计数，没有侧栏会话树 / 轨迹回看页 |
| 会话删除未加固 | 目前唯一会「破坏性丢数据」的路径（误删不可恢复） |
| 计划历史入口 | 接口可按来源查询，侧栏入口未做 |

## 13. 一页速查表

| 概念 | 一句话 |
| --- | --- |
| 谁在跑 | 租约：`进程号 + 本次开机标识`，TTL 30s，每 10s 续期，存在任务自己身上 |
| 怎么知道人跑了 | 租约到期 + 任务还在进行（**不区分**崩溃/强杀/优雅退出，因为库里长得一样） |
| 手上正在干什么 | 在飞：`none` / `write` / `unknown` 三级；bash 复用审批规则判定 |
| 为什么还要「最近副作用」 | 工具结束 ≠ 步骤完成；只看在飞会把「写完没打勾就被杀」误判成「两步之间」→ 重复写 |
| 恢复怎么决定 | 无副作用 → 自动；有副作用 + 有产物声明 → 看文件在不在；否则 → 人来确认 |
| 为什么不停下来自己干 | **代价不对称**：把「已落地」当「没落地」会重复副作用、不可逆 |
| 观测怎么保证不影响主链路 | 唯一插桩点 + 内部永不抛错 + 队列攒批 + 超限丢最旧 + 失败降级 + **可整体关闭** |
| run 的边界 | `agent_settled`（不是「开始」——重试/压缩会多次开始） |
| 失败率为什么准 | 策略拦截（审批/规划期/兜底）与真实失败分开统计 |
| 读路径为什么不慢 | 计数/成本走**写入时维护的预聚合表**，分位数走**有界样本** |
| 任务状态从哪来 | 从步骤**聚合**（唯一真相源），只有「取消」冻结 |
| 并发怎么防覆盖 | 单条 SQL 乐观锁 + 版本号，409 带当前真实版本 |
| 版本号管什么 | **只管用户可见内容**；心跳/租约/在飞不占版本号 |
| 观测与任务的区别 | 一个可丢可降级，一个必须同步落库、失败冒泡 |
| Plan 是什么 | **Task 的受控视图**（同一个 id、同一张表、同一份状态） |
| 规划期怎么只读 | 审批规则 → 命令逐段拆解 → **未归类即不放行**；最终靠调用拦截兑现 |
| 为什么改工具集很贵 | 工具列表在请求最前面，改一次让**整段前缀缓存失效** |
| 为什么子会话不能递归 | **结构保证**：到深度上限的会话根本不注册这个工具 |
| 子会话的成本算谁的 | **父任务**：它继承父会话的任务绑定 |
| 子会话审批弹在哪 | **父会话**的界面（子会话没有界面，没人订阅它的流） |
| 子会话失败怎么告诉父会话 | 作为**结果**返回（只有「没起来」才是异常） |

## 14. 面试速答汇编

**通用**

- **「这套东西的核心价值是什么？」** → 把 agent 从「黑盒跑一段就完了」变成
  **可记账（M1）、可控制（M2）、可恢复（M3）、可验证（M4）、可委派（M5）**。
- **「你怎么保证不加新功能时行为不变？」** → 每个模块都有「关掉后行为与之前完全一致」的开关或空实现
  （trace 可整体关闭、恢复只列不跑、子会话能力显式关闭）。

**M1**

- 会不会拖慢 agent？→ 单条开销 p95 0.011ms，批量 flush 才是可见的那几毫秒。
- 为什么不用 OTel？→ 单机自托管，要 SQL + 面板，不要 collector；可关、可离线更重要。
- 数据丢了怎么办？→ 分两层：明细可清、队列可丢（都计数且面板可见）；聚合口径不受影响。

**M2**

- 为什么任务表不存「进度百分比」？→ 状态能从步骤算出来，就不存第二份。
- 并发冲突怎么办？→ 409 + 当前版本，前端刷新重试一次；**先减少冲突面（运行时写入不占版本号），再处理冲突**。
- 任务和 trace 为什么不同写入路径？→ 一致性要求不同（§6.3）。

**M3**

- 为什么不用行锁？→ 锁绑连接，崩溃即悬空；租约用「到期时间」代替「探活」。
- 为什么 owner 要带开机标识？→ 让「重启」天然使旧租约不再被续期，省掉一整套探测逻辑。
- 凭什么不会重复副作用？→ 三道防线 + 自动路径不存在重放。

**M4**

- 模型乱来怎么办？→ 不依赖自觉：参数结构化 + 错误可读 + 状态机只认工具调用 + 关键状态只有用户能推进。
- 为什么不让模型决定何时开始执行？→ **规划是免费的，执行是不可逆的**，推进权必须在人手里。
- 怎么证明能跑？→ 单测（边界）+ spike（真实 SDK 端到端、断言零标记）+ eval（golden set + 门禁）。
- 为什么 eval 里失败率 16.7% 不算糟？→ 它**包含刻意制造的拒绝**，价值在**可比性**而不在绝对值。

**M5**

- 子 agent 共享上下文吗？→ 不共享，**这是目的不是缺陷**（双向隔离）。
- 为什么不起子进程？→ 会丢掉四样东西：审批通道、trace 树、租约/任务绑定、离线可测。
- 怎么防止子 agent 失控？→ 三道：结构（不能递归）、预算（轮数/token/时限）、闸门（排队）。
- 和官方最关键的区别？→ 官方是「另一个进程里的 pi」，我们是「同一个运行时里的另一个会话」；
  **差别的全部后果都来自这一个决定。**
